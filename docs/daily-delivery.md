# 每日飞书报告的跨运行去重

每日工作流可能先手动补跑，几个小时后又收到同一交易日的 `schedule` 事件。`concurrency: stock-analysis` 只能让两次运行依次执行；进程内 `NOTIFICATION_DEDUP_TTL_SECONDS` 无法记住另一个 runner 已发送的报告。

`.github/workflows/00-daily-analysis.yml` 使用发送前意向（intent）和发送后回执（receipt）artifact 保存跨运行证据，默认按 **工作流、行情日、飞书目标指纹、报告组件** 判断是否允许发送。触发方式、run ID、股票名单、模型文案和规则版本均不构成另一个发送名额。原工作日北京时间18:07的cron不变，本功能不保证GitHub准时触发，也没有新增自动补跑调度器。

## 发送顺序

1. 原有选股步骤先确定 `as_of`。跨午夜的已完成交易日沿用该日期，不能以生成时间或runner的UTC自然日代替。未运行形态筛选的入口在09:00后沿用北京时间日期契约；09:00前没有核验行情日则停止，避免把昨晚消息记为新一天。该入口不能证明休市日强制分析取得的是当日行情。
2. `scripts/daily_delivery.py prepare` 读取同仓库、同一每日工作流、主分支的历史意向与回执，验证元数据和JSON结构后生成本次文件。API读取、下载或验证失败时停止，不能视为“从未发送”。
3. `actions/upload-artifact` 必须先成功上传意向，后面的分析与发送步骤才执行。仓库权限只有 `contents: read`、`actions: read`，不需要仓库写权限或新建外部存储。
4. 飞书传输层在每个实际请求返回后记录ACK、明确拒绝或未知结果；只有HTTP 200且业务码为数值0才确认接收。模型完成、其他渠道成功、工作流绿色均不能替代飞书ACK。
5. 阶段结束时封口组件回执。工作流以 `always()` 核对并上传独立的终态artifact，即使模型或发送失败也保留已经产生的证据。未封口或请求中断的记录不能推断为送达成功。

形态筛选明确输出 `market_closed` 时，沿用原先正常休市跳过，不准备凭证、不进入分析或发送；较旧的最近交易日不会使正常休市变成凭证错误。

意向和回执位于本次 `reports/daily_delivery/intent.json`、`receipt.json`，并以包含日期、run ID及attempt的独立artifact名称保存30天，不覆盖旧运行记录。凭证只记录目标哈希及状态，不保存Webhook原文、签名密钥或App Secret。原 `analysis-reports-*` 仍包含普通报告及日志。

## 组件和重试

| 组件 | 覆盖内容 | 与其他组件的关系 |
| --- | --- | --- |
| `stocks` | 个股汇总或单股推送组成的当次股票日报 | 已发股票报告不会压掉尚未发的大盘 |
| `market` | 当次大盘复盘，沿用原区域配置 | `market-only`与完整模式共用这份记录 |
| `document` | 可选飞书文档链接通知 | 独立于股票正文和大盘正文 |

已确认送达的组件跳过飞书POST，并明确记录“已发送跳过”；其他通知渠道照常执行。默认的完整模式分别处理股票和大盘。仅在显式日报上下文中启用该凭证，普通告警、会话回复、Web通知测试、本地/Docker/API默认行为及原有进程内降噪不变；本次未启用或新增图表推送。

没有实际尝试发送、或全部请求均明确被拒绝且没有ACK时，后续运行可再次尝试。已有成功批次、请求超时、断连、非JSON成功响应、未取得终态回执等情况不能视为全部未送，后续自动运行会保守暂停该组件。部分批次或部分单股成功时不会把新生成的文案按旧批号拼接续传，以免内容遗漏或重复。日报作用域内，未知提交结果也不会自动降级成纯文本再发一遍；明确业务拒绝仍可按原有方式降级。

单股模式按整批判断完成：某只报告生成失败或整次逻辑发送失败后，后续另一只得到ACK不能抹掉先前失败。生成失败不会伪造POST或超时证据；如果该批没有任何ACK或未知请求，后续新运行仍可完整重试，本次核对则显示失败。

可选合并报告同时占用 `stocks` 和 `market`。若两者一份已送、一份未送，不能原样再次发送包含两份正文的合并消息；应选择 `stocks-only` 或 `market-only` 补相应部分，或明确确认重发。

## 人工确认重发

GitHub的 **Run workflow → 确认重发当日飞书报告**（`resend_daily`）默认关闭。确需重发时新建一次手动运行并开启；这可能再次发送已经送达的批次或单股。许可只在新的 `workflow_dispatch` 第一次attempt生效，点击“Re-run jobs”不会继承无限重发许可。所有旧凭证保留。

`force_run`依然只控制交易日检查，不会跳过发送记录。`DAILY_DELIVERY_FILE`是工作流内部交接路径，不应写进`.env`，不作为新的持久配置入口。

## 边界与迁移

Webhook没有跨运行的服务端幂等键。如果飞书已接收消息但响应丢失，不能同时保证“自动补齐”和“绝不重复”；本功能优先暂停未知结果，交由人工确认。意向上传成功但runner随后消失、回执上传失败也按未知处理。记录被人为删除或超过保留期后无法保证历史去重，不能将此功能描述为严格的“恰好一次”。

首次部署当天，若历史旧版运行已经尝试发送但缺少新凭证，不能仅凭工作流成功就认定已送或未送；准备步骤核对旧报告的行情日，无法证明未发送时按未知处理。这样可避免升级后立即再次发送同日旧报告。

本地回归使用离线GitHub响应、真实凭证文件和模拟HTTP/SDK响应覆盖跨实例恢复、失败、部分批次、未知结果、不同目标、人工重发及入口路由；不需要实际调用模型或发飞书。发布时应另外记录远端CI结果和未执行的在线外发验收。

回滚：revert该修复即可移除工作流凭证步骤及显式日报上下文，无数据库迁移；旧artifact可保留作审计。回滚后恢复原先跨运行可能重复推送的行为。
